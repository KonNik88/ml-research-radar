# Saved Research Collections v0.1

## Document status

```text
contract_version = v0.1
decision_status = accepted
implementation_status = migration foundation in progress
product_mode = local single-user
canonical_truth = false
mutates_canonical_documents = false
search_backend_independent = true
durable_user_state = true
```

This document defines the first persistent user-workflow capability in
ML Research Radar.

The capability turns a transient discovery session into a resumable workflow:

```text
discover paper
→ save to collection
→ annotate and track reading status
→ close the application
→ return later without losing state
```

The contract is intentionally bounded. It defines storage, lifecycle, API, and
validation semantics for Collections v0.1 without introducing accounts,
sharing, recommendations, or a new paper truth layer.

---

## 1. Accepted product scope

Collections v0.1 supports:

- named collections;
- an optional collection description;
- adding and removing canonical papers;
- an optional note per saved paper;
- a reading status per saved paper;
- persistence across API and UI restarts;
- persistence across canonical Postgres replacement/refresh;
- listing orphaned saved items whose paper is absent from the current corpus;
- save/remove actions from the existing paper-discovery surfaces;
- a dedicated Collections UI surface.

The accepted reading statuses are:

```text
to_read
reading
read
```

The default is `to_read`.

### 1.1 Explicit non-goals

The following are outside v0.1:

- authentication and user accounts;
- multi-user ownership or authorization;
- collection sharing;
- nested collections;
- tags or tag hierarchies;
- drag-and-drop ordering;
- saved searches and watchlists;
- notifications;
- collection export;
- Paper Comparison;
- Research Trail;
- recommendations;
- synchronization with external reference managers.

These features require separate contracts and must not expand this slice.

---

## 2. Data ownership boundary

ML Research Radar now has two data planes with different lifecycle rules.

| Plane | Examples | Lifecycle |
|---|---|---|
| Derived research data | canonical papers, retrieval indexes, Postgres serving tables, artifacts, clusters, graphs | Rebuildable and replaceable |
| Durable workspace data | collections, saved-paper membership, notes, reading statuses | User-authored and non-rebuildable |

The paper-level source of truth remains:

```text
data/analytics/reconciled/canonical_documents.jsonl
```

Collections never redefine paper identity, reconciliation, ranking, provenance,
or retrieval output. They store only user state associated with a
`canonical_id`.

### 2.1 Storage boundary

Durable workspace state is stored in the same PostgreSQL instance but in a
separate schema:

```text
workspace.research_collections
workspace.research_collection_items
```

The workspace schema:

- is managed by Alembic;
- is not managed by `store/sql/*.sql`;
- is not owned by `scripts/export/export_postgres_v1.py`;
- is not owned by `scripts/export/export_artifacts_postgres_v1.py`;
- must not be truncated or recreated during a canonical refresh;
- must work regardless of whether search uses the `file` or `db` backend.

The existing `PostgresDocumentStore` remains a derived paper-serving store.
Workspace persistence will use a separate store and service boundary.

## 3. Relational contract

### 3.1 `workspace.research_collections`

| Column | Type | Null | Semantics |
|---|---|---:|---|
| `collection_id` | UUID | no | Stable application-generated collection identity |
| `name` | TEXT | no | Trimmed display name, 1–200 characters |
| `description` | TEXT | yes | Optional description, at most 2,000 characters |
| `created_at` | TIMESTAMPTZ | no | Database creation timestamp |
| `updated_at` | TIMESTAMPTZ | no | Last user-visible collection update |

Rules:

- `collection_id` is the primary key;
- UUID values are generated by the application, not by a database extension;
- collection names are unique after `lower(btrim(name))`;
- `Research`, `research`, and ` Research ` therefore conflict;
- the service trims `name` before persistence;
- the service writes `updated_at` when the name, description, or membership
  changes;
- the database default initializes both timestamps;
- v0.1 does not add a timestamp trigger.

### 3.2 `workspace.research_collection_items`

| Column | Type | Null | Semantics |
|---|---|---:|---|
| `collection_id` | UUID | no | Owning collection |
| `canonical_id` | TEXT | no | Soft reference to a canonical paper |
| `note` | TEXT | yes | Optional user note, at most 20,000 characters |
| `reading_status` | TEXT | no | `to_read`, `reading`, or `read` |
| `added_at` | TIMESTAMPTZ | no | First time the paper was saved to this collection |
| `updated_at` | TIMESTAMPTZ | no | Last note/status update |

Rules:

- `(collection_id, canonical_id)` is the primary key;
- one paper can appear at most once in one collection;
- one paper may appear in multiple collections;
- `collection_id` references
  `workspace.research_collections(collection_id) ON DELETE CASCADE`;
- `canonical_id` deliberately has no foreign key to `canonical_documents`;
- deleting a collection explicitly deletes its items;
- replacing, truncating, or temporarily losing a canonical paper never deletes
  a collection item;
- `canonical_id` must contain at least one non-whitespace character;
- the service writes `updated_at` when `note` or `reading_status` changes;
- changing only a paper's derived metadata does not change workspace timestamps.

An index on `canonical_id` supports reverse lookup and orphan audits. The
primary key already supports listing items by collection.

## 4. Paper-link and orphan semantics

Collection membership is a soft reference:

```text
research_collection_items.canonical_id
        - - - - - - - - - - - - - - ->
current canonical corpus
```

The API validates that a paper exists when a new item is added. After the item
exists, the workspace record is durable.

If a later refresh does not contain that `canonical_id`:

- the item remains stored;
- its note, status, and timestamps remain stored;
- reads expose it as orphaned/unavailable in the current corpus;
- the integrity validator reports it;
- no automatic deletion or identity substitution occurs.

If the same `canonical_id` returns in a later corpus, normal hydration resumes
without modifying the workspace row.

Collections v0.1 does not copy canonical titles, abstracts, authors, or other
paper metadata into the durable tables. Current metadata is hydrated from the
active corpus; an orphaned item falls back to its `canonical_id`.

---

## 5. Mutation semantics

### 5.1 Collection names

Before persistence, the service:

1. trims leading and trailing whitespace;
2. rejects an empty result;
3. enforces the 200-character limit.

Name conflicts are case-insensitive under the PostgreSQL `lower` behavior used
by the unique index.

### 5.2 Add or update item

The public add operation is idempotent:

```text
PUT /collections/{collection_id}/items/{canonical_id}
```

For a new item:

- the paper must exist in the current corpus;
- missing `reading_status` becomes `to_read`;
- `added_at` and `updated_at` are initialized.

For an existing item:

- repeating the request does not create a duplicate;
- omitted `note` or `reading_status` does not erase the stored value;
- explicitly supplied fields update only those fields;
- `added_at` is preserved.

An already saved orphan may be edited or removed even while its paper is
absent. Re-adding a new, previously unseen orphan is rejected.

### 5.3 Deletion

The only v0.1 actions allowed to remove workspace rows are:

- deleting a specific collection item;
- explicitly deleting a collection, which cascades to that collection's items.

Canonical exporters, refresh pipelines, retrieval rebuilds, graph builders, and
artifact exporters are not deletion authorities for workspace data.

## 6. API surface

The accepted v0.1 routes are:

```text
POST   /collections
GET    /collections
GET    /collections/{collection_id}
PATCH  /collections/{collection_id}
DELETE /collections/{collection_id}

PUT    /collections/{collection_id}/items/{canonical_id}
PATCH  /collections/{collection_id}/items/{canonical_id}
DELETE /collections/{collection_id}/items/{canonical_id}
```

Stable domain error codes:

```text
collection_not_found
collection_name_conflict
paper_not_found
collection_item_not_found
workspace_unavailable
validation_error
```

The workspace API is available with both search backends. File-backed search
does not imply file-backed user state: Collections still require the workspace
PostgreSQL connection.

API schemas, status codes, pagination, and response payloads will be fixed in
the Store + API implementation party before those routes are exposed.

## 7. Migration ownership and operation

Alembic owns only the durable `workspace` schema in this slice.

The standard `public.alembic_version` table is the migration ledger. It stores
only the current revision identifier and is not part of the paper serving or
workspace domain model.

Initial revision:

```text
20260728_0001_create_workspace_collections
```

The migration:

- creates the schema if absent;
- creates the two tables, constraints, and indexes;
- does not inspect or modify canonical rows;
- does not add a foreign key to `canonical_documents`;
- does not edit `store/sql/01_schema.sql` or other init SQL;
- has a reversible downgrade for disposable test databases.

The migration reads:

```text
ML_RADAR_WORKSPACE_DATABASE_URL
```

when explicitly set. Otherwise it composes the connection from the existing:

```text
ML_RADAR_POSTGRES_HOST
ML_RADAR_POSTGRES_PORT
ML_RADAR_POSTGRES_DBNAME
ML_RADAR_POSTGRES_USER
ML_RADAR_POSTGRES_PASSWORD
```

Destructive downgrade is a test/development operation only. Once user-authored
state exists, application rollback must leave newer workspace tables in place.

## 8. Required validation

### 8.1 Migration contract checks

The no-database smoke suite must verify:

- one Alembic head exists;
- offline PostgreSQL SQL renders successfully;
- the two tables are created under `workspace`;
- the normalized-name uniqueness rule exists;
- item uniqueness exists;
- reading-status validation exists;
- the only item foreign key targets its collection with `ON DELETE CASCADE`;
- no reference to `canonical_documents` exists in migration SQL;
- old init SQL does not claim workspace ownership;
- downgrade SQL contains no `CASCADE` schema drop.

### 8.2 PostgreSQL integration checks

Only a clearly named disposable test database may be used. The suite must:

- read its explicit connection from
  `ML_RADAR_WORKSPACE_TEST_DATABASE_URL`;
- refuse the operational `ml_radar` database;
- skip when no test database URL is supplied;
- apply `upgrade head` to a clean workspace;
- confirm the schema, tables, columns, keys, checks, and indexes through the
  PostgreSQL catalog;
- prove a second `upgrade head` is a no-op;
- prove duplicate items, invalid statuses, and normalized duplicate names are
  rejected;
- prove migration upgrade/downgrade does not alter an existing
  `canonical_documents` table;
- downgrade only the workspace migration.

### 8.3 Full vertical-slice Definition of Done

The complete Collections v0.1 slice is done only when this scenario passes on
a disposable database:

```text
find paper
→ create collection
→ save paper
→ add note and reading status
→ restart API and UI
→ reopen collection
→ run canonical replace/refresh rehearsal
→ confirm the collection, note, and status survived
→ inspect orphan reporting if the paper was absent
```

---

## 9. Implementation sequence

1. Contract and Alembic migration foundation.
2. Separate workspace store, service, schemas, errors, and API router.
3. Collections UI and reusable save/remove actions.
4. Orphan validator, refresh-survival rehearsal, regression checks, and
   documentation/current-state update.

This sequence is additive. It does not reopen completed provenance, graph,
Qdrant, source-ingestion, ranking, or dataset-release decisions.
